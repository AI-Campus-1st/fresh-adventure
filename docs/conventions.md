# 협업 규칙

4개 레포(메인·data·fe·be)에 공통으로 적용합니다.

## 1. 브랜치

| 브랜치 | 용도 |
| --- | --- |
| `main` | 항상 동작하는 상태. 직접 push 금지, PR로만 병합 |
| `feat/<작업>` | 기능 개발 (예: `feat/kamis-collector`) |
| `fix/<작업>` | 버그 수정 |
| `docs/<작업>` | 문서 작업 (예: `docs/weekly-01`) |

- 작업 단위는 작게 나누고, 이슈 번호가 있으면 브랜치명에 붙입니다 (예: `feat/12-kamis-collector`).
- 메인 레포의 주간일지처럼 가벼운 문서는 `main`에 바로 커밋해도 됩니다.

## 2. 커밋 메시지

`<타입>: <요약>` 형식, 요약은 한국어로 씁니다.

| 타입 | 의미 |
| --- | --- |
| `feat` | 새 기능 |
| `fix` | 버그 수정 |
| `docs` | 문서 |
| `refactor` | 동작 변화 없는 구조 개선 |
| `test` | 테스트 추가·수정 |
| `chore` | 설정, 빌드, 의존성 등 |

예: `feat: KAMIS 일별 소매가 수집기 추가`

## 3. Pull Request

- PR 템플릿을 채우고, 팀원 1명 이상 리뷰 후 병합합니다.
- 병합 방식은 Squash merge를 기본으로 합니다.

## 4. API 키·비밀값 관리 (기획안 5-7, 11장)

- 데이터랩 Client ID는 **BI엔지니어 1명만** 관리하고, 서버 환경변수로만 둡니다. 팀원 공유·GitHub 업로드 금지 (NAVER API HUB 약관 7.2②).
- 팀원별 키로 나눠 호출해 한도를 늘리지 않습니다 (약관 7.3⑤).
- 공공데이터포털·KOSIS·LLM 키, DB 접속 정보도 같은 방식으로 관리합니다.
- 각 레포에는 `.env.example`(키 이름만)을 두고, 실제 값은 `.env`에 넣습니다. `.env`는 `.gitignore`로 제외합니다.
- **Public 레포(메인·fe)** 에는 어떤 비밀값도 두지 않습니다. 실수로 올렸다면 커밋을 지우는 것만으로는 부족하니 **즉시 키를 재발급**하세요.

## 5. 데이터 파일

- 원본 데이터는 S3, 정제 데이터는 RDS에 둡니다. 레포에는 CSV·Parquet 등 데이터 파일을 올리지 않습니다.
- 데이터랩 수집값은 재제공 금지(약관 7.3⑥)이므로 Public 레포·노트북 출력에 원본 수치를 남기지 않습니다.
