## 1. 프로젝트 개요

**fresh adventure: 식품 커머스 MD·마케터를 위한 신선식품(과일·채소) 수요·프로모션 의사결정 플랫폼**

## 2. 기획 배경

온라인 신선식품 시장은 커지고 있지만, 신선식품은 계절에 따라 수요와 가격이 크게 바뀌어 판매 시점과 타깃을 잘못 잡으면 재고가 폐기로 이어진다.

2026년 9월 온라인쇼핑 거래액 중 농축수산물은 1조 6,738억 원으로 전년 동월 대비 9.7% 늘었고, 식품(음·식료품+농축수산물) 거래의 80.1%가 모바일에서 일어났다([국가데이터처 온라인쇼핑동향](https://m.korea.kr/archive/expDocView.do?docId=41945), [보도](https://sateconomy.co.kr/news/view/1065588973230533)). 명절 직전에는 농축수산물 온라인 거래가 크게 늘어난다. 2017년 1월\~2026년 9월 KOSIS 온라인쇼핑동향에서 설·추석 18회를 보면, 명절 직전 2주가 걸친 달의 농축수산물 거래액은 앞뒤 달 평균보다 평균 27.1% 많았고(18회 중 16회 증가), 명절과 무관한 달은 평균 -0.4%였다(팀 분석, 5-2).

식품 커머스 MD·마케터가 겪는 문제는 다음과 같다.

- 어떤 품목의 관심도가 언제 오르기 시작하는지 미리 알기 어려움
- 품목별로 주 구매 고객층(성별·연령)과 채널(모바일·PC)을 데이터로 판단하기 어려움
- 제철·명절 프로모션을 경험에 기대어 기획함
- 시장 가격이 내려 '가격 소구'가 가능한 품목을 놓침
- 원가가 급등할 품목을 행사 상품으로 잡아 마진이 깎임
- 관심도·가격·시장 데이터가 기관별로 흩어져 있음

fresh adventure는 흩어진 공공 데이터를 하나의 화면에 모아, 판매·홍보 결정을 데이터로 뒷받침한다.

## 4. 핵심 기능

메인은 수요 쪽 기능 4개(4-1\~4-4)이고, 원가 리스크(4-5)는 프로모션에서 빼야 할 품목을 걸러 주는 보조 기능이다. AI 리포트(4-6)가 이를 한 번에 묶는다.

### 4-1. 수요 트렌드

**의사결정:** 지금 어떤 품목에 관심이 몰리고, 온라인 식품 시장은 어느 쪽으로 커지는가?

- 품목별 검색·쇼핑 클릭 관심도 추이 (주 단위, 전년 동기 대비)
- 관심도 급증 품목 탐지, 연관 키워드 묶음 (예: 배추·절임배추·김장)
- 온라인 식품 시장 규모: 농축수산물·음식료품 월별 온라인 거래액과 모바일 비중 (KOSIS는 품목별로 나오지 않아 상위 상품군인 농축수산물로 본다)

KPI: 관심도 지수, 관심도 증가율(주·전년), 온라인 거래액 증감률, 모바일 비중

### 4-2. 타깃 고객 분석

**의사결정:** 이 품목은 누구에게, 어떤 기기로 알려야 하는가?

- 쇼핑인사이트 성별·연령대·기기(PC/모바일)별 클릭 비중
- 품목별 핵심 고객층과 시즌에 따른 변화 (예: 김장철 배추 관심의 연령대 이동)
- 타깃·채널 제안: 광고 타깃팅 후보, 모바일 푸시 우선 여부

### 4-3. 시즌·프로모션 캘린더

**의사결정:** 어떤 품목을 언제 행사로 내야 하는가?

- 품목별 관심도 피크 시점과 상승 시작 시점 (과거 패턴 기반 예측)
- 제철·명절·기념일(특일정보)과 관심도를 겹친 월별 프로모션 캘린더
- 프로모션 후보 점수 (초안, 데이터 분포를 보고 조정)

**마케팅 적기 분석 (v3.1 추가)**

**의사결정:** 이 품목의 광고·기획전을 몇 주 전에 시작하고, 언제 끝내야 하는가?

관심도가 피크일 때 행사를 시작하면 이미 늦다. 관심이 오르기 시작하는 시점에 노출을 시작해야 피크 구간의 수요를 잡을 수 있다. 그래서 피크만이 아니라 "상승 시작 → 피크 → 하락"의 흐름과 그 사이 간격을 품목별로 측정한다.

| 분석 항목 | 내용 | 데이터 |
| --- | --- | --- |
| 상승 시작 주 | 관심도가 연평균 대비 일정 기준 이상 오르기 시작하는 첫 주 (변화점 탐지) | 검색어·쇼핑 클릭 추이 |
| 피크 주·하락 주 | 연중 최고 주와, 피크의 절반 아래로 떨어지는 주 | 검색어·쇼핑 클릭 추이 |
| 리드타임 | 피크 주 − 상승 시작 주 = 사전 마케팅에 쓸 수 있는 기간 | 위 결과 |
| 검색 → 쇼핑 시차 | 검색 관심도가 쇼핑 클릭보다 몇 주 앞서는지 (교차상관) → 검색이 오르면 "구매 직전"까지 남은 기간 | 검색어 + 쇼핑 클릭 |
| 타깃별 시차 | 성별·연령대별 상승 시작 주 차이 → 먼저 반응하는 타깃부터 광고 | 쇼핑인사이트 성별·연령 |
| 명절 기준 패턴 | 설·추석 D-주차별 관심도 변화 → 명절 상품 노출 시작 주 (사과·배 등 선물 품목) | 특일정보 + 관심도 |
| 적기 안정성 | 연도별 상승 시작 주의 편차 → 편차가 작으면 신뢰도 높음 (A·B·C 등급) | 2017년 이후 연도별 결과 |

**출력:** 품목별 "권장 마케팅 시작 주 / 행사 집중 주 / 종료 주"와 신뢰도 등급을 프로모션 캘린더에 표시한다. 예: "참외: 4월 2주 노출 시작 → 5월 3주\~6월 2주 집중 → 7월 1주 종료 (신뢰도 A)"

**검증:** 2017\~2023년 패턴으로 2024\~2025년 상승 시작 주를 예측하고, 실제와의 주차 오차를 잰다 (6장 백테스트와 같은 방식).

**한계:** 실제 광고 집행·매출 성과 데이터가 없으므로, 결과는 "관심도 기준 적기"이지 매출을 최대화하는 시점을 증명한 것은 아니다.

### 4-4. 상품 원가 및 예상 수익성 분석

**의사결정:** 이 상품을 얼마에 팔아야 남고, 몇 개를 팔아야 손해를 보지 않는가?

시장 가격과 원재료 매입가에 운영 비용을 반영해 상품 1개당 원가와 예상 이익을 계산하고, 판매량에 따른 수익성 변화를 비교한다. 온라인 경쟁 가격은 합법적 수집 경로가 없어(5-6) KAMIS 소매가(대형유통·전통시장 실제 판매가)를 시장 가격 기준으로 쓴다.

| 분석 항목 | 내용 | 데이터 |
| --- | --- | --- |
| 원재료별 구매가격 | 품목별 kg당 매입가, 산지·등급·규격별 비교 | KAMIS 중도매가 (산지·등급·크기 비교는 도매시장 정산정보) |
| 상품 1개당 원재료 원가 | 상품 용량(예: 1.5kg) × kg당 매입가 | 계산 |
| 포장비·배송비 | 박스·완충재·아이스팩, 건당 배송비 | 사용자 입력 |
| 플랫폼 수수료 | 판매가 × 수수료율 | 사용자 입력 |
| 광고·홍보비 | 판매가 대비 비율 또는 월 고정 금액 | 사용자 입력 |
| 예상 폐기비 | 원재료 원가 × 폐기율 | 사용자 입력 |
| 적정 판매가격 | 목표 마진율로 계산한 판매가를 시장 가격대(KAMIS 소매가)와 비교 | 계산 + KAMIS |
| 판매량별 예상 매출·이익 | 판매량 시나리오별 매출, 총비용, 이익 | 계산 |
| 손익분기점 | 손해를 보지 않는 최소 판매량 | 계산 |

**계산식**

- 1개당 변동비 = 원재료 원가 + 포장비 + 배송비 + 폐기비 + 판매가 × (수수료율 + 광고비율)
- 1개당 이익 = 판매가 − 1개당 변동비
- 예상 이익 = 1개당 이익 × 판매량 − 고정비(월 광고비 등)
- 손익분기 판매량 = 고정비 ÷ 1개당 이익
- 적정 판매가 = (원재료 원가 + 포장비 + 배송비 + 폐기비) ÷ (1 − 수수료율 − 광고비율 − 목표 마진율)

**함께 보는 지표**

- 가격 소구 후보: 소매가가 평년보다 낮아진 품목 ("지금이 제일 쌀 때" 행사)
- 원가 낮은 조합: 산지·등급·크기별 kg당 매입가 비교 → 산지 마케팅(예: 고랭지 배추, 제주 감귤), 크기 구성(예: 사과 대과 vs 중과), 소포장·대용량 구성
- 매입가 민감도: 매입가가 10·20% 오르면 이익과 손익분기점이 어떻게 변하는지 (4-5 원가 리스크와 연결)

**데이터 범위 (v3.1 명확화):** 실데이터로 자동 반영되는 항목은 원재료 구매가격(KAMIS 중도매가)과 시장 가격대(KAMIS 소매가)뿐이다. 포장비·배송비·플랫폼 수수료·광고비·폐기율·판매량은 공공데이터가 없으므로 사용자가 입력하는 시나리오로 두고, 팀이 정한 기본값과 그 출처(플랫폼 공개 수수료표 등)를 화면에 표시한다. 도매 단위(10kg 상자 등)를 g당 가격으로 바꾸는 단위 환산표와, 시연용 샘플 상품 3\~5개의 구성표(BOM)를 1\~2단계에서 만든다. 과거 가격 변동 분포(상·하위 10%)를 적용해 예상 이익을 한 값이 아니라 범위로 보여 준다.

**출력:** 품목별 원가 구조 표, 적정 판매가와 시장 가격대 비교, 판매량–이익 그래프(손익분기점 표시). 실제 판매자 비용 데이터는 없으므로 비용 항목은 사용자가 입력하는 시나리오 방식이며, 결과는 '예상' 수익성으로 표기한다.

### 4-5. 원가 리스크 경보 (보조)

**의사결정:** 이 품목은 행사를 미루거나 빼야 하는가?

- 출력: 품목별 위험 등급(낮음·보통·높음) → 4-3 프로모션 점수의 '원가 안정성'에 반영

### 4-6. AI 마케팅 리포트

AI는 DB의 분석 결과를 근거로만 답한다.

- 주간 수요 브리핑: 급상승 품목, 다가오는 시즌, 이번 주 마케팅 시작 권장 품목(적기 분석), 가격 소구 후보

**테스트에서 확인한 주의점**

- **분석 기간:** 관심도는 2016년(쇼핑 클릭 2017년 8월)부터, 가격은 KAMIS 1996년부터, 정산정보는 2018년부터 있다. 백테스트(2019\~2024년)와 평년(최근 5년 평균) 지수를 위해 **과일·채소의 매입가와 원가 지표는 KAMIS 중도매가로 계산**하고, 정산정보는 산지·등급·크기 비교(4-4)에만 쓴다. 정산정보로 5년 평년을 만들 수 있는 것은 2023년부터다.
- 정산정보 산지명(`plor_nm`)은 대표 품목 기준 2019년 67\~98%(딸기가 가장 낮음), 2025년 99\~100% 채워져 있다. 예전 증빙 파일의 '산지명 1%'는 하루 전체가 아니라 API 첫 페이지(1,000건)만 센 값이다. 첫 페이지에는 산지명이 빈 거래가 몰려 있어(2019년 1\~9%) 하루 전체(80\~82%)나 대표 품목(76\~79%)과 크게 다르므로, 채움 비율은 하루치를 모두 받아 품목 단위로 계산한다. 표기가 섞여 있어(`충남`/`충청남도`, 뒤 공백, 현재 행정구역명 소급 적용) 산지코드(`plor_cd`) 기준으로 묶는다. 산지에 `중국` 등 수입산도 있어 국내 산지 분석에서는 뺀다.
- 정산정보의 크기코드 `100`, 등급코드 `10`, 단위코드 `10`은 '값 없음'(`.`)이다. 코드 칸은 100% 차 있지만 실제 정보는 아니므로 이 코드를 빼고 계산한다. 크기 정보는 과일(사과 94\~98%·배 97%·복숭아 89\~96%·참외 87\~90%)은 높고 채소(감자 18\~27%·양파 22\~34%·대파 31\~35%)는 낮아, 크기별 분석은 크기 정보가 많은 품목(주로 과일)에서만 쓴다.
- KAMIS는 제철에만 가격이 조사된다(예: 복숭아·참외는 11월 0건, 딸기·감귤은 8월 0건, 제철에는 정상 조회). 평년 대비 가격 지수와 가격 소구 후보는 품목별 출하 기간 안에서만 계산한다.
- KAMIS 품목명이 정산정보와 다른 경우가 있다(대파 → `파`, 마늘 → `깐마늘(국산)`, 깐마늘은 1996년 중도매가 없음). 매핑표에서 맞춘다.
- 정산정보 소분류(품종)는 품목에 따라 52\~100%만 구분되어 있고 나머지는 `기타`이거나 비어 있다. 품종 대신 거래 월과 산지로 구분하는 방법을 함께 쓴다(예: 여름배추 = 7\~9월·강원산).
- KAMIS는 2022년부터 '친환경농산물' 구분이 추가되어, 일반 상품과 분리해 집계한다.
- KAMIS 소매 조사 시장은 대형유통이 `A-유통`·`B-유통`처럼 익명으로, 전통시장은 시장명(`경동`·`부전` 등)으로 나온다. 시장 유형 매핑표를 만든다.
- KAMIS 품목코드는 부류+품목 코드로 지정하며 추측하면 틀린다(예: `600/619`는 물오징어). 대표 품목 코드는 코드 목록에서 확인한다.

4. **집계:** 품목·주 단위 마트(`agg_weekly_item`)를 만든다.
5. **점검:** 수집 실패·건수 급감을 로그로 남기고 재수집한다.

**AI 리포트 활용 원칙:** 데이터랩에는 AI 활용을 금지하는 명시 조항이 없지만, 7.3 ③의 '제공 취지' 문구에 해석의 여지가 있다. 그래서 (1) AI에는 원본 수치가 아닌 파생 지표(예: 4주 증가율, 피크까지 남은 주)만 입력하고, (2) 설정 하나로 데이터랩 근거를 AI 입력에서 뺄 수 있게 만들며, (3) 네이버클라우드 고객지원에 활용 가능 여부를 문의해 답변을 근거로 남긴다.

### 5-9. 보류 데이터: 축산물 (한우·돼지고기)

축산물은 데이터 호출 테스트는 통과했지만, 아래 문제 때문에 이번 프로젝트(2027년 1월 6일 마감)에서는 보류한다. 일정에 여유가 생기거나 최종 발표 이후 확장할 때 다시 검토한다. 테스트 결과는 재개할 때 쓰도록 여기에 남긴다.

| 문제 | 내용 |

| 별도 서버·XML | 공공데이터포털이 아닌 축산물품질평가원 서버이고 XML로만 응답하며, 데이터셋 2개를 따로 활용신청해야 해 1주차 BI 작업이 늘어난다 |

## 6. 분석 방법

데이터는 일 단위로 수집하고 주 단위로 분석한다. 관심도와 가격은 일별 출렁임과 결측(주말·공휴일)이 커서, 마케팅 의사결정 단위인 주로 묶는다.

| 기능 | 분석 방법 |
| --- | --- |
| 4-1 수요 트렌드 | 관심도 증가율(주·전년 대비), 급증 탐지(최근 8주 평균 대비 Z-점수), STL 분해로 계절성 제거 후 추세 판단, 온라인 거래액 전년 동월 대비 |
| 4-2 타깃 고객 | 성별·연령대·기기별 클릭 비중과 시즌별 변화, 품목 간 고객 구성 비교(군집화로 비슷한 품목 묶기) |
| 4-3 시즌·프로모션 | 품목별 연간 피크·상승 시작 주차 추정, 명절 전후 관심도·가격 변화(이벤트 분석), 프로모션 후보 다기준 점수, 마케팅 적기 분석(변화점 탐지로 상승 시작 주, 리드타임, 검색→쇼핑 교차상관 시차, 성별·연령별 상승 시차, 연도별 편차로 신뢰도) |
| 4-4 원가·수익성 분석 | 원가 구조 모델(원재료·포장·배송·수수료·광고·폐기), 목표 마진율 기반 적정 판매가, 판매량 시나리오별 손익과 손익분기점(BEP), 매입가 변동 민감도 분석, 소매가 평년 대비 지수, kg당 매입가 분포(산지·등급·크기) |
| 4-5 원가 리스크 | 원가 지표(KAMIS 중도매가)와 거래량의 평년 대비 이상 탐지, 가격 예측(전주·계절 평균 기준 모델 대비 SARIMA·Prophet·LightGBM 비교), 여름배추 기상-가격 시차 분석 |
| 4-6 AI 리포트 | LLM + SQL 기반 질의응답, 분석 결과 테이블을 근거로 인용 |

예측 모델은 시계열 순서를 유지한 학습·검증·테스트 분할을 쓰고 MAE·RMSE로 평가한다.

**여름배추 기상-가격 검증 (4-5의 시제품)**

1. 여름배추 주산지인 강원의 대관령·강릉·태백 관측소 폭염일수·누적 강수량을 주 단위로 만든다. (1996년\~, 테스트 통과. 정산정보 기준 8월 가락시장 배추 물량의 52\~68%가 강원산)
2. STL로 가격(KAMIS 배추 중도매가)의 계절성을 빼고, 기상 지표를 1\~12주 밀어 가며 시차 상관을 본다.
3. 기상 변수를 넣은 예측 모델의 오차가 줄면 경보에 쓰고, 줄지 않으면 가격·거래량 이상 탐지만 쓴다.
4. 2023년 8월(고온으로 평년 대비 48% 상승) 사례에서 경보가 제때 나왔는지 확인한다. 선행연구([KREI, 최병옥 외 2020](https://repository.krei.re.kr/handle/2018.oak/24802))와 결과 방향을 비교한다.

### 분석 검증 계획

판매·프로모션 성과 데이터가 없어도, 아래 4가지 검증으로 분석 결과의 신뢰도를 숫자로 제시한다.

| 검증 | 질문 | 방법 | 성능 지표 |
| --- | --- | --- | --- |
| ① 대리지표 검증 | 관심도가 실제 온라인 매출 흐름을 따라가는가? | 월별 신선식품(과일·채소) 관심도 지수와 KOSIS 농축수산물 온라인 거래액(실제 금액)의 상관과 시차 상관, 계절성 제거 후 비교 (거래액은 품목별로 나오지 않고 분석에서 뺀 수산물·축산물도 포함되어 추세·시차 중심으로 해석) | 상관계수, 관심도가 거래액을 앞서는 개월 수 |
| ② 백테스트 | 그때 이 추천을 따랐다면 맞았을까? | 2019\~2024년 각 시점에서 당시 데이터만으로 프로모션 후보·피크 시점을 만들고, 이후 4주의 실제 관심도·가격과 비교 | 피크 시점 오차(주), 방향 적중률(%), 기준 모델(작년 같은 주) 대비 MAE 개선율 |
| ③ 원가 경보 정밀도 | 위험하다고 한 품목이 실제로 올랐나? | 과거 경보 시점 이후 4\~8주 원가 지표(4-5의 분야별 지표) 변화 확인, 여름배추는 2023년 8월 사례 포함 | 정밀도·재현율(%), 경보 선행 주수 |
| ④ 적기 예측 검증 | 권장한 마케팅 시작 주가 실제 관심도 상승 시작과 맞았나? | 2017\~2023년 패턴만으로 2024\~2025년 품목별 상승 시작·피크 주를 예측하고 실제와 비교 | 상승 시작 주 평균 오차(주), ±2주 이내 적중률(%), 기준 모델(작년 같은 주) 대비 개선 |

모든 검증은 시계열 순서를 지켜(미래 정보 사용 금지) 수행하고, 결과가 기준 모델보다 나아지지 않는 기능은 대시보드에서 '참고용'으로 표시한다.

| `fact_cost_risk` | 품목·주별 원가 위험 등급과 근거 | 분석 결과 |
| `fact_forecast` | 관심도 피크·가격 예측 결과 | 분석 결과 |
| `fact_marketing_timing` | 품목·연도별 상승 시작·피크·하락 주, 리드타임, 검색→쇼핑 시차, 성별·연령별 상승 시차, 권장 시작·집중·종료 주, 신뢰도 등급 | 분석 결과 |
| `dim_product_bom` | 샘플 상품별 원재료 구성(재료·중량) | 수작업 |
| `dim_unit_conv` | 품목·포장 단위(10kg 상자, 망 등)를 g당 가격으로 바꾸는 환산 계수 | ④⑤ + 수작업 |
| `ai_reports` | AI 리포트와 근거 테이블·수치 | AI |

수익성 분석을 위해 `dim_cost_scenario`(사용자가 입력한 포장비·배송비·수수료율·광고비·폐기율·고정비·목표 마진율)와 `fact_profit_sim`(품목·시나리오·판매량별 매출·비용·이익·손익분기점)를 둔다.

## 8. 대시보드와 기술 스택

대시보드는 직접 만든 웹 화면(FastAPI + 프런트엔드)으로 구현해 AWS에 배포한다.

| 화면 | 주요 내용 |
| --- | --- |
| 메인 (이번 주 브리핑) | 관심도 급상승 품목, 이번 주 마케팅 시작 권장 품목, 다가오는 시즌, 프로모션 추천 Top 5, 원가 위험 품목 |
| 수요 트렌드 | 품목별 관심도 추이, 연관 키워드, 온라인 식품 시장 규모 |
| 타깃 고객 | 성별·연령대·기기별 비중, 시즌별 변화, 타깃 제안 |
| 시즌·프로모션 캘린더 | 월별 캘린더(제철·명절·피크), 품목별 마케팅 시작·집중·종료 주와 신뢰도(적기 분석), 프로모션 후보 점수 |
| 원가·수익성 | 품목별 원가 구조, 적정 판매가와 시장 가격대, 판매량–이익 그래프와 손익분기점, 산지·등급·크기별 kg당 매입가, 가격 소구 후보, 원가 위험 |
| AI 마케팅 어시스턴트 | 주간 리포트, 자연어 질의응답 |

**구현 순서 (v3.1):** 1차 발표(12/18)까지 메인·수요 트렌드·원가·수익성 3개 화면을 로컬에서 실제 데이터로 완성하고(10장 '1차 발표 시연 범위'), 타깃 고객·시즌·프로모션 캘린더·AI 마케팅 어시스턴트는 1차 발표 이후(4주차)에 추가한다. 1차 발표 때 메인 화면의 원가 위험 품목과 마케팅 시작 권장 품목은 아직 계산 전이므로 '준비 중'으로 표시한다. 화면에 들어갈 수치는 데이터분석이 결과 테이블로 완성해 넘기고(1주차에 명세 확정, 12/13 최종 전달), BI는 조회·표시만 한다.

| 구분 | 기술 |
| --- | --- |
| 수집·전처리 | Python, Requests, Pandas, NumPy |
| 원본 저장 | Amazon S3 |
| 데이터베이스 | Amazon RDS for PostgreSQL |
| 파이프라인 | Python ETL + 스케줄러 (EC2 cron, 필요 시 EventBridge + Lambda) |
| 분석·ML | Scikit-learn, Statsmodels, Prophet, LightGBM |
| AI | LLM API, SQL 기반 질의응답 |
| 백엔드 | FastAPI (Amazon EC2, Docker) |
| 프런트엔드 | 웹 프레임워크 + 차트 라이브러리 (예: React + Plotly.js, 팀 합의로 확정), S3 + CloudFront 배포 |
| 협업 | Git, GitHub |

**AWS 흐름:** EC2 스케줄러가 API 원본을 S3에 저장 → ETL이 RDS에 적재 → 주 1회 분석 배치가 점수·예측·위험 등급 저장 → FastAPI가 화면용 API와 AI 리포트 제공 → 프런트(S3 + CloudFront)가 표시.

**비용:** 데이터는 무료이고 AWS는 사용량 과금이다. 개발은 로컬 Docker에서 하고, AWS는 최소 사양으로 시연 기간에만 켜며 AWS Budgets 예산 알림을 건다.

**1차 발표(12/18) 시연 범위**

| 화면 | 1차 발표에 나와야 하는 것 | 데이터 | 담당 (결과 → 화면) | 1차에서 빠지는 것 |

**일정이 밀릴 때 줄일 범위 (우선순위 낮은 것부터)**

1. 관세청 수입·KOSIS 생산량 분석 → 보류
2. 예측 모델 비교(SARIMA·Prophet·LightGBM) → 기준 모델 + 1개만
3. 고객 구성 군집화 → 성별·연령 비중 비교만
4. 산지·등급·크기별 세부 비교 → 품목 단위 평년 대비 가격 지수만
5. AI 자연어 질의응답 → 주간 리포트 생성만
6. 대표 품목 15개 → 10개 (과일·채소 각 4개 이상 유지)

메인 분석(수요 트렌드, 마케팅 적기, 원가·수익성)과 검증은 줄이지 않는다.

## 11. 팀 구성과 역할

역할은 "경영·마케팅이 기준을 정하고, 데이터분석이 계산해 결과 테이블로 넘기고, BI가 수집과 화면을 구현한다"는 원칙으로 나눈다. v3.1에서는 BI엔지니어에 몰린 개발 작업을 덜고, 경영·마케팅도 직접 분석 결과물을 갖도록 조정했다. 조장은 경영 담당 이선진이고, 이 프로젝트의 아이디어는 BI엔지니어 김민지가 제안했다.

- 데이터랩 호출(쇼핑인사이트 포함)은 키를 가진 BI만 실행한다. 다른 팀원은 요청 목록을 주고 DB에 적재된 결과를 쓴다 (약관 7.2②).
- 데이터분석은 분석 결과를 화면용 결과 테이블로 완성해 넘기고, BI는 조회와 표시만 한다.
- 경영·마케팅의 직접 분석은 SQL·피벗·간단한 파이썬 수준으로 하고, 방법이 어려운 부분(변화점 탐지, 교차상관)은 데이터분석이 지원한다.
- GitHub 브랜치·리뷰로 코드를 관리하고, 단계가 끝날 때마다 팀 회의로 다음 단계를 결정한다.

**API 키 관리 규칙** (NAVER API HUB 약관 7.2 ②·7.3 ⑤, 5-7 참고)

- 데이터랩 Client ID는 애플리케이션 1개에 1개만 발급하고, BI엔지니어(김민지) 1명이 관리한다.
- 키는 서버 환경변수로만 두고 팀원에게 공유하거나 GitHub에 올리지 않는다. 다른 팀원은 DB에 적재된 결과만 쓴다.
- 팀원별 키로 나눠 호출해 한도를 늘리지 않는다.
- 공공데이터포털·KOSIS 키도 같은 방식(서버 보관, 저장소 업로드 금지)으로 관리한다. 공공데이터포털 키 하나로 ④⑤⑥⑦⑨⑩을 모두 쓰지만, 데이터셋마다 활용신청은 따로 해야 한다.
