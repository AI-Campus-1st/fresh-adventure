## 2. 기획 배경

온라인 신선식품 시장은 커지고 있지만, 신선식품은 계절에 따라 수요와 가격이 크게 바뀌어 판매 시점과 타깃을 잘못 잡으면 재고가 폐기로 이어진다.

2026년 9월 온라인쇼핑 거래액 중 농축수산물은 1조 6,738억 원으로 전년 동월 대비 9.7% 늘었고, 식품(음·식료품+농축수산물) 거래의 80.1%가 모바일에서 일어났다([국가데이터처 온라인쇼핑동향](https://m.korea.kr/archive/expDocView.do?docId=41945), [보도](https://sateconomy.co.kr/news/view/1065588973230533)). 명절이 있는 달에는 농축수산물 거래가 눈에 띄게 늘어난다.

식품 커머스 MD·마케터가 겪는 문제는 다음과 같다.

- 어떤 품목의 관심도가 언제 오르기 시작하는지 미리 알기 어려움
- 품목별로 주 구매 고객층(성별·연령)과 채널(모바일·PC)을 데이터로 판단하기 어려움
- 제철·명절 프로모션을 경험에 기대어 기획함
- 시장 가격이 내려 '가격 소구'가 가능한 품목을 놓침
- 원가가 급등할 품목을 행사 상품으로 잡아 마진이 깎임
- 관심도·가격·시장 데이터가 기관별로 흩어져 있음

FreshLens는 흩어진 공공 데이터를 하나의 화면에 모아, 판매·홍보 결정을 데이터로 뒷받침한다.

## 4. 핵심 기능

메인은 수요 쪽 기능 4개(4-1\~4-4)이고, 원가 리스크(4-5)는 프로모션에서 빼야 할 품목을 걸러 주는 보조 기능이다. AI 리포트(4-6)가 이를 한 번에 묶는다.

### 4-1. 수요 트렌드

**의사결정:** 지금 어떤 품목에 관심이 몰리고, 온라인 식품 시장은 어느 쪽으로 커지는가?

- 품목별 검색·쇼핑 클릭 관심도 추이 (주 단위, 전년 동기 대비)
- 관심도 급증 품목 탐지, 연관 키워드 묶음 (예: 배추·절임배추·김장)
- 온라인 식품 시장 규모: 농축수산물·음식료품 월별 온라인 거래액과 모바일 비중

KPI: 관심도 지수, 관심도 증가율(주·전년), 온라인 거래액 증감률, 모바일 비중

### 4-2. 타깃 고객 분석

**의사결정:** 이 품목은 누구에게, 어떤 기기로 알려야 하는가?

- 쇼핑인사이트 성별·연령대·기기(PC/모바일)별 클릭 비중
- 품목별 핵심 고객층과 시즌에 따른 변화 (예: 김장철 배추 관심의 연령대 이동)
- 타깃·채널 제안: 광고 타깃팅 후보, 모바일 푸시 우선 여부

### 4-3. 시즌·프로모션 캘린더

**의사결정:** 어떤 품목을 언제 행사로 내야 하는가?

- 품목별 관심도 피크 시점과 상승 시작 시점 (과거 패턴 기반 예측)
- 제철·명절·기념일(특일정보)과 관심도를 겹친 월별 프로모션 캘린더
- 프로모션 후보 점수 (초안, 데이터 분포를 보고 조정)

| 평가 지표 | 배점 | 내용 |
| --- | --- | --- |
| 관심도 모멘텀 | 30 | 최근 4주 관심도 증가율 |
| 시즌 적합도 | 25 | 과거 피크 시점·제철·명절과의 거리 |
| 가격 매력도 | 25 | 소매가의 평년·전년 대비 수준 (쌀수록 유리) |
| 원가 안정성 | 20 | 4-5 원가 리스크가 낮을수록 유리 |
| 합계 | 100 | 프로모션 후보 우선순위 |

**마케팅 적기 분석 (v3.1 추가)**

**의사결정:** 이 품목의 광고·기획전을 몇 주 전에 시작하고, 언제 끝내야 하는가?

관심도가 피크일 때 행사를 시작하면 이미 늦다. 관심이 오르기 시작하는 시점에 노출을 시작해야 피크 구간의 수요를 잡을 수 있다. 그래서 피크만이 아니라 "상승 시작 → 피크 → 하락"의 흐름과 그 사이 간격을 품목별로 측정한다.

| 분석 항목 | 내용 | 데이터 |
| --- | --- | --- |
| 상승 시작 주 | 관심도가 연평균 대비 일정 기준 이상 오르기 시작하는 첫 주 (변화점 탐지) | 검색어·쇼핑 클릭 추이 |
| 피크 주·하락 주 | 연중 최고 주와, 피크의 절반 아래로 떨어지는 주 | 검색어·쇼핑 클릭 추이 |
| 리드타임 | 피크 주 − 상승 시작 주 = 사전 마케팅에 쓸 수 있는 기간 | 위 결과 |
| 검색 → 쇼핑 시차 | 검색 관심도가 쇼핑 클릭보다 몇 주 앞서는지 (교차상관) → 검색이 오르면 "구매 직전"까지 남은 기간 | 검색어 + 쇼핑 클릭 |
| 타깃별 시차 | 성별·연령대별 상승 시작 주 차이 → 먼저 반응하는 타깃부터 광고 | 쇼핑인사이트 성별·연령 |
| 명절 기준 패턴 | 설·추석 D-주차별 관심도 변화 → 명절 상품 노출 시작 주 | 특일정보 + 관심도 |
| 적기 안정성 | 연도별 상승 시작 주의 편차 → 편차가 작으면 신뢰도 높음 (A·B·C 등급) | 2017년 이후 연도별 결과 |

**출력:** 품목별 "권장 마케팅 시작 주 / 행사 집중 주 / 종료 주"와 신뢰도 등급을 프로모션 캘린더에 표시한다. 예: "참외: 4월 2주 노출 시작 → 5월 3주\~6월 2주 집중 → 7월 1주 종료 (신뢰도 A)"

**검증:** 2017\~2023년 패턴으로 2024\~2025년 상승 시작 주를 예측하고, 실제와의 주차 오차를 잰다 (6장 백테스트와 같은 방식).

**한계:** 실제 광고 집행·매출 성과 데이터가 없으므로, 결과는 "관심도 기준 적기"이지 매출을 최대화하는 시점을 증명한 것은 아니다.

### 4-4. 상품 원가 및 예상 수익성 분석

**의사결정:** 이 상품을 얼마에 팔아야 남고, 몇 개를 팔아야 손해를 보지 않는가?

시장 가격과 원재료 매입가에 운영 비용을 반영해 상품 1개당 원가와 예상 이익을 계산하고, 판매량에 따른 수익성 변화를 비교한다. 온라인 경쟁 가격은 합법적 수집 경로가 없어(5-6) KAMIS 소매가(대형마트·전통시장 실제 판매가)를 시장 가격 기준으로 쓴다.

| 분석 항목 | 내용 | 데이터 |
| --- | --- | --- |
| 원재료별 구매가격 | 품목별 kg당 매입가, 산지·등급별 비교 | KAMIS 도매가, 도매시장 정산정보 |
| 상품 1개당 원재료 원가 | 상품 용량(예: 1.5kg) × kg당 매입가 | 계산 |
| 포장비·배송비 | 박스·완충재·아이스팩, 건당 배송비 | 사용자 입력 |
| 플랫폼 수수료 | 판매가 × 수수료율 | 사용자 입력 |
| 광고·홍보비 | 판매가 대비 비율 또는 월 고정 금액 | 사용자 입력 |
| 예상 폐기비 | 원재료 원가 × 폐기율 | 사용자 입력 |
| 적정 판매가격 | 목표 마진율로 계산한 판매가를 시장 가격대(KAMIS 소매가)와 비교 | 계산 + KAMIS |
| 판매량별 예상 매출·이익 | 판매량 시나리오별 매출, 총비용, 이익 | 계산 |
| 손익분기점 | 손해를 보지 않는 최소 판매량 | 계산 |

**계산식**

- 1개당 변동비 = 원재료 원가 + 포장비 + 배송비 + 폐기비 + 판매가 × (수수료율 + 광고비율)
- 1개당 이익 = 판매가 − 1개당 변동비
- 예상 이익 = 1개당 이익 × 판매량 − 고정비(월 광고비 등)
- 손익분기 판매량 = 고정비 ÷ 1개당 이익
- 적정 판매가 = (원재료 원가 + 포장비 + 배송비 + 폐기비) ÷ (1 − 수수료율 − 광고비율 − 목표 마진율)

**함께 보는 지표**

- 가격 소구 후보: 소매가가 평년보다 낮아진 품목 ("지금이 제일 쌀 때" 행사)
- 원가 낮은 조합: 산지·등급·크기별 kg당 매입가 비교 → 산지 마케팅, 소포장·대용량 구성
- 매입가 민감도: 도매가가 10·20% 오르면 이익과 손익분기점이 어떻게 변하는지 (4-5 원가 리스크와 연결)

**데이터 범위 (v3.1 명확화):** 실데이터로 자동 반영되는 항목은 원재료 구매가격(KAMIS 소매가·도매 정산정보)뿐이다. 포장비·배송비·플랫폼 수수료·광고비·폐기율·판매량은 공공데이터가 없으므로 사용자가 입력하는 시나리오로 두고, 팀이 정한 기본값과 그 출처(플랫폼 공개 수수료표 등)를 화면에 표시한다. 도매 단위(10kg 상자 등)를 g당 가격으로 바꾸는 단위 환산표와, 시연용 샘플 상품 3\~5개의 구성표(BOM)를 1\~2단계에서 만든다. 과거 가격 변동 분포(상·하위 10%)를 적용해 예상 이익을 한 값이 아니라 범위로 보여 준다.

**출력:** 품목별 원가 구조 표, 적정 판매가와 시장 가격대 비교, 판매량–이익 그래프(손익분기점 표시). 실제 판매자 비용 데이터는 없으므로 비용 항목은 사용자가 입력하는 시나리오 방식이며, 결과는 '예상' 수익성으로 표기한다.

### 4-5. 원가 리스크 경보 (보조)

**의사결정:** 이 품목은 행사를 미루거나 빼야 하는가?

- 도매가·거래량의 평년 대비 급변 탐지 (전 품목)
- 기상 기반 가격 상승 위험: 여름(고랭지)배추로 먼저 검증하고 효과가 확인되면 노지 채소로 확대
- 출력: 품목별 위험 등급(낮음·보통·높음) → 4-3 프로모션 점수의 '원가 안정성'에 반영

### 4-6. AI 마케팅 리포트

AI는 DB의 분석 결과를 근거로만 답한다.

- 주간 수요 브리핑: 급상승 품목, 다가오는 시즌, 가격 소구 후보
- 프로모션 후보와 근거, 타깃·채널 제안, 원가 위험 품목 경고
- 자연어 질의응답 (예: "다음 달 30대 여성 대상 과일 행사 후보는?")
- 네이버 데이터랩은 원본 수치 대신 파생 지표만 AI에 입력하고, 설정으로 제외할 수 있게 만든다 (5-7 약관 검토 결과)

### 5-5. 데이터 처리 흐름

1. **수집:** API별 수집기가 정해진 주기로 호출하고 원본 응답을 S3에 저장한다. (가격·정산·기상 매일, 데이터랩 주 1회, 온라인쇼핑·수입 월 1회)
2. **정제:** 타입 변환, 결측·이상치 처리, kg 표준화, 코드→명칭 복원을 한다.
3. **통합:** `map_product_code`로 출처별 품목을 연결하고 품목·날짜 기준으로 RDS에 적재한다.
4. **집계:** 품목·주 단위 마트(`agg_weekly_item`)를 만든다.
5. **점검:** 수집 실패·건수 급감을 로그로 남기고 재수집한다.

| 7.3 ⑤ 다수 키로 한도 확대 금지 | 같은 목적의 앱에서 키 여러 개로 호출 금지 | 팀원별 키로 나눠 수집하지 않음 |
| 7.3 ④ 광고 금지 | 결과 화면에 광고 노출 금지 | 광고 없음 |
| 7.3 ⑨ BI 가이드 | 네이버 브랜드 사용 규칙 준수 | 차트에 "자료: 네이버 데이터랩" 출처 표기 |
| 7.3 ⑫ 과부하 금지 | 자동화 프로그램으로 과부하를 일으키는 접속 금지 | 주 1회 수집, 한도(월 50,000건) 내 운영 |
| 8.1\~8.2 권리 귀속 | 결과 데이터 권리는 네이버, 이용자는 제한된 사용권만 보유 | 데이터 소유권을 주장하지 않음 |

**AI 리포트 활용 원칙:** 데이터랩에는 AI 활용을 금지하는 명시 조항이 없지만, 7.3 ③의 '제공 취지' 문구에 해석의 여지가 있다. 그래서 (1) AI에는 원본 수치가 아닌 파생 지표(예: 4주 증가율, 피크까지 남은 주)만 입력하고, (2) 설정 하나로 데이터랩 근거를 AI 입력에서 뺄 수 있게 만들며, (3) 네이버클라우드 고객지원에 활용 가능 여부를 문의해 답변을 근거로 남긴다.

## 6. 분석 방법

데이터는 일 단위로 수집하고 주 단위로 분석한다. 관심도와 가격은 일별 출렁임과 결측(주말·공휴일)이 커서, 마케팅 의사결정 단위인 주로 묶는다.

| 기능 | 분석 방법 |
| --- | --- |
| 4-1 수요 트렌드 | 관심도 증가율(주·전년 대비), 급증 탐지(최근 8주 평균 대비 Z-점수), STL 분해로 계절성 제거 후 추세 판단, 온라인 거래액 전년 동월 대비 |
| 4-2 타깃 고객 | 성별·연령대·기기별 클릭 비중과 시즌별 변화, 품목 간 고객 구성 비교(군집화로 비슷한 품목 묶기) |
| 4-3 시즌·프로모션 | 품목별 연간 피크·상승 시작 주차 추정, 명절 전후 관심도·가격 변화(이벤트 분석), 프로모션 후보 다기준 점수, 마케팅 적기 분석(변화점 탐지로 상승 시작 주, 리드타임, 검색→쇼핑 교차상관 시차, 성별·연령별 상승 시차, 연도별 편차로 신뢰도) |
| 4-4 원가·수익성 분석 | 원가 구조 모델(원재료·포장·배송·수수료·광고·폐기), 목표 마진율 기반 적정 판매가, 판매량 시나리오별 손익과 손익분기점(BEP), 매입가 변동 민감도 분석, 소매가 평년 대비 지수, 산지·등급·크기별 kg당 가격 분포 |
| 4-5 원가 리스크 | 도매가·거래량의 평년 대비 이상 탐지, 가격 예측(전주·계절 평균 기준 모델 대비 SARIMA·Prophet·LightGBM 비교), 여름배추 기상-가격 시차 분석 |
| 4-6 AI 리포트 | LLM + SQL 기반 질의응답, 분석 결과 테이블을 근거로 인용 |

예측 모델은 시계열 순서를 유지한 학습·검증·테스트 분할을 쓰고 MAE·RMSE로 평가한다.

**여름배추 기상-가격 검증 (4-5의 시제품)**

1. 대관령·강릉·태백(여름배추 8월 가락시장 반입의 93%) 관측소의 폭염일수·누적 강수량을 주 단위로 만든다. (1996년\~, 테스트 통과)
2. STL로 가격의 계절성을 빼고, 기상 지표를 1\~12주 밀어 가며 시차 상관을 본다.
3. 기상 변수를 넣은 예측 모델의 오차가 줄면 경보에 쓰고, 줄지 않으면 가격·거래량 이상 탐지만 쓴다.
4. 2023년 8월(고온으로 평년 대비 48% 상승) 사례에서 경보가 제때 나왔는지 확인한다. 선행연구([KREI, 최병옥 외 2020](https://repository.krei.re.kr/handle/2018.oak/24802))와 결과 방향을 비교한다.

### 분석 검증 계획

판매·프로모션 성과 데이터가 없어도, 아래 3가지 검증으로 분석 결과의 신뢰도를 숫자로 제시한다.

| 검증 | 질문 | 방법 | 성능 지표 |
| --- | --- | --- | --- |
| ① 대리지표 검증 | 관심도가 실제 온라인 매출 흐름을 따라가는가? | 월별 농축수산물 관심도 지수와 KOSIS 온라인 거래액(실제 금액)의 상관과 시차 상관, 계절성 제거 후 비교 | 상관계수, 관심도가 거래액을 앞서는 개월 수 |
| ② 백테스트 | 그때 이 추천을 따랐다면 맞았을까? | 2019\~2024년 각 시점에서 당시 데이터만으로 프로모션 후보·피크 시점을 만들고, 이후 4주의 실제 관심도·가격과 비교 | 피크 시점 오차(주), 방향 적중률(%), 기준 모델(작년 같은 주) 대비 MAE 개선율 |
| ③ 원가 경보 정밀도 | 위험하다고 한 품목이 실제로 올랐나? | 과거 경보 시점 이후 4\~8주 도매가 변화 확인, 여름배추는 2023년 8월 사례 포함 | 정밀도·재현율(%), 경보 선행 주수 |

모든 검증은 시계열 순서를 지켜(미래 정보 사용 금지) 수행하고, 결과가 기준 모델보다 나아지지 않는 기능은 대시보드에서 '참고용'으로 표시한다.

품목과 날짜(주)를 기준으로 결합하는 스타 스키마(star schema)로, Amazon RDS(PostgreSQL)에 둔다.

| `dim_product` | 품목·품종·부류, 대표 품목 여부 | ⑥ |

| `dim_date` | 날짜·주·월·계절, 공휴일·명절·명절 전 구간 | ⑩ |

## 8. 대시보드와 기술 스택

대시보드는 직접 만든 웹 화면(FastAPI + 프런트엔드)으로 구현해 AWS에 배포한다.

| 화면 | 주요 내용 |
| --- | --- |
| 메인 (이번 주 브리핑) | 관심도 급상승 품목, 다가오는 시즌, 프로모션 추천 Top 5, 원가 위험 품목 |
| 수요 트렌드 | 품목별 관심도 추이, 연관 키워드, 온라인 식품 시장 규모 |
| 타깃 고객 | 성별·연령대·기기별 비중, 시즌별 변화, 타깃 제안 |
| 시즌·프로모션 캘린더 | 월별 캘린더(제철·명절·피크), 프로모션 후보 점수 |
| 원가·수익성 | 품목별 원가 구조, 적정 판매가와 시장 가격대, 판매량–이익 그래프와 손익분기점, 가격 소구 후보, 원가 위험 |
| AI 마케팅 어시스턴트 | 주간 리포트, 자연어 질의응답 |

| 구분 | 기술 |
| --- | --- |
| 수집·전처리 | Python, Requests, Pandas, NumPy |
| 원본 저장 | Amazon S3 |
| 데이터베이스 | Amazon RDS for PostgreSQL |
| 파이프라인 | Python ETL + 스케줄러 (EC2 cron, 필요 시 EventBridge + Lambda) |
| 분석·ML | Scikit-learn, Statsmodels, Prophet, LightGBM |
| AI | LLM API, SQL 기반 질의응답 |
| 백엔드 | FastAPI (Amazon EC2, Docker) |
| 프런트엔드 | 웹 프레임워크 + 차트 라이브러리 (예: React + Plotly.js, 팀 합의로 확정), S3 + CloudFront 배포 |
| 협업 | Git, GitHub |

**AWS 흐름:** EC2 스케줄러가 API 원본을 S3에 저장 → ETL이 RDS에 적재 → 주 1회 분석 배치가 점수·예측·위험 등급 저장 → FastAPI가 화면용 API와 AI 리포트 제공 → 프런트(S3 + CloudFront)가 표시.

**비용:** 데이터는 무료이고 AWS는 사용량 과금이다. 개발은 로컬 Docker에서 하고, AWS는 최소 사양으로 시연 기간에만 켜며 AWS Budgets 예산 알림을 건다.

## 9. 차별성과 기대 효과

기존 서비스가 관심도(데이터랩)와 가격(KAMIS)을 따로 보여주는 반면, FreshLens는 둘을 원가 위험까지 묶어 "이번 주 무엇을 누구에게 팔지"를 바로 제안한다.

| 기존 | FreshLens |
| --- | --- |
| 데이터랩: 키워드별 관심도 조회 | 품목·고객층·시즌을 겹친 프로모션 후보 점수 |
| KAMIS: 가격 조회 | 가격 소구 후보와 원가 위험 판단 |
| 과거 데이터 조회 | 관심도 피크·가격 예측 |
| 마케터가 직접 해석 | 근거가 달린 AI 주간 리포트 |

- **MD·마케터:** 행사 시점·타깃을 데이터로 정하고, 원가 급등 품목을 행사에서 피해 마진을 지킨다. 시장 조사 시간이 줄어든다.
- **기업:** 데이터 기반 프로모션 운영 체계, 시장 변화 자동 모니터링
- **기술:** 다중 공공 API 파이프라인, DW·마트 설계, 이기종 코드 매핑, 시계열 분석·예측, AWS 기반 웹 대시보드와 AI 서비스

## 10. 한계, 리스크, 진행 순서

핵심 데이터 8종은 호출이 확인됐고, 데이터 한계는 6장의 분석 검증 계획으로 보완한다. 데이터랩 약관은 검토를 마쳤고(5-7), 남은 가장 큰 리스크는 쇼핑인사이트 성별·연령 조회 확인이다.

**진행 순서**

1. **데이터 검증:** 8종 API 호출 통과(완료). 쇼핑인사이트 성별·연령·기기, KOSIS 온라인쇼핑동향 확인이 남음(약관 검토 완료).
2. **MVP:** 대표 품목 15개의 수요 트렌드·타깃·시즌 분석과 프로모션 점수, 여름배추 원가 리스크 검증.
3. **전체 구축:** 파이프라인 자동화 → 웹 대시보드 → AI 리포트 → AWS 배포.

**분석상 한계와 보완**

| 한계 | 영향 | 보완 방법 |
| --- | --- | --- |
| 검색·클릭 관심도는 상대값이며 판매량이 아님 | 일부 | 피크 시점·증가율·고객 비중 등 비율·타이밍 분석에는 충분. 판매 흐름과의 관계는 검증 ①(KOSIS 실제 거래액)으로 확인, 품목 간 비교는 기준 키워드로 재정규화 |
| 네이버 이용자 편향 | 약함 | 국내 최대 검색·쇼핑 플랫폼이라 대리지표로 사용, 해석 시 명시 |
| 온라인 경쟁사 판매가·매출·재고 없음 (합법적 수집 경로 없음) | 큼 (가격 기능) | 범위에서 제외(5-6). 시장 가격 기준은 KAMIS 소매가(대형마트·전통시장 실제 판매가, 1996년\~)로 세우고, 가격 기능은 '시장 가격대 참고·가격 소구 후보·마진 시뮬레이션'으로 한정 |
| 프로모션 성과 데이터 없음 | 보완 가능 | 효과 예측은 하지 않고, 추천의 적중 여부를 검증 ②(백테스트)로 측정 |
| 기상과 가격은 상관관계 | 보완 가능 | 계절성 제거, 수입량·거래량 통제, 기준 모델 대비 예측 개선으로 판단하고 인과는 단정하지 않음. 정부 비축 방출은 보도자료로 사례를 표시 |
| 도매시장 정산정보는 2018년 1월부터 | 거의 없음 | 2018\~2026년 약 8년·400주 이상으로 주 단위 계절성 분석에 충분. 핵심 데이터인 데이터랩은 2016년, KAMIS·ASOS는 1996년부터 |

## 11. 팀 구성과 역할

역할은 "경영·마케팅이 기준을 정하고, 데이터분석이 계산해 결과 테이블로 넘기고, BI가 수집과 화면을 구현한다"는 원칙으로 나눈다. v3.1에서는 BI엔지니어에 몰린 개발 작업을 덜고, 경영·마케팅도 직접 분석 결과물을 갖도록 조정했다. 이름은 팀 합의 후 채운다.

| 희망 직무 | 역할 | 주요 담당 | 직접 분석 | 포트폴리오 산출물 |

| 경영 | PM·비즈니스 전략 | 문제 정의·일정·범위 관리, 원가·수익성 기획 총괄(계산식, 샘플 상품 구성표, 비용 기본값과 출처), 네이버 등 외부 문의, 검증 결과 해석, 최종 발표 | 프로모션 점수 가중치 설계와 계산(SQL) | 기획서, 원가·수익성 모델, 프로모션 점수 설계서, 발표 자료 |

| 담당 | v3 | v3.1 | 비고 |
| --- | --- | --- | --- |
| 경영 | 약 15% | 약 22% | 원가·수익성 기획과 점수 계산 추가 |
| 마케팅 | 약 20% | 약 25% | 타깃 분석·적기 분석을 직접 수행 |

| BI엔지니어 | 약 35% | 약 27% | 분석 계산은 데이터분석이 맡고, 화면은 단계적으로 구현 |

| 단계 | 경영 | 마케팅 | 데이터분석 | BI엔지니어 |
| --- | --- | --- | --- | --- |
| 1. 데이터 검증 | 약관 확인, 범위 확정, 네이버 문의 | 대표 품목·키워드 15개 선정 | 쇼핑인사이트 테스트 요청 목록 작성, 단위 환산 필드 확인 | 추가 API 테스트(쇼핑인사이트 포함) 실행, 코드 매핑 |
| 2. MVP | 프로모션 점수 기준 확정, 샘플 상품 구성표·비용 기본값 | 타깃·시즌 분석, 적기 분석 초안, 화면 기획 | 수요 분석, 여름배추 검증, 원가 계산 모듈 | 대표 품목 적재, 주 단위 마트, 핵심 화면 3개(메인·수요 트렌드·원가·수익성) |
| 3. 전체 구축 | 점수 계산, 검증 결과 해석, 발표 준비 | 캘린더·적기 리포트, AI 프롬프트, 시연 시나리오 | 예측·원가 리스크 고도화, 마진 범위·민감도, 검증 3종 | 나머지 화면 3개, AI 연결, AWS 배포 |

- 데이터랩 호출(쇼핑인사이트 테스트 포함)은 키를 가진 BI만 실행한다. 다른 팀원은 요청 목록을 주고 DB에 적재된 결과를 쓴다 (약관 7.2②).
- 데이터분석은 분석 결과를 화면용 결과 테이블로 완성해 넘기고, BI는 조회와 표시만 한다.
- 경영·마케팅의 직접 분석은 SQL·피벗·간단한 파이썬 수준으로 하고, 방법이 어려운 부분(변화점 탐지, 교차상관)은 데이터분석이 지원한다.
- GitHub 브랜치·리뷰로 코드를 관리하고, 단계가 끝날 때마다 팀 회의로 다음 단계를 결정한다.

**API 키 관리 규칙** (NAVER API HUB 약관 7.2 ②·7.3 ⑤, 5-7 참고)

- 데이터랩 Client ID는 애플리케이션 1개에 1개만 발급하고, BI엔지니어 1명이 관리한다.
- 키는 서버 환경변수로만 두고 팀원에게 공유하거나 GitHub에 올리지 않는다. 다른 팀원은 DB에 적재된 결과만 쓴다.
- 팀원별 키로 나눠 호출해 한도를 늘리지 않는다.
- 공공데이터포털·KOSIS 키도 같은 방식(서버 보관, 저장소 업로드 금지)으로 관리한다.

## 12. 최종 정의

FreshLens는 네이버 데이터랩의 검색·쇼핑 관심도, 온라인쇼핑 거래액, 시장 소매가, 도매시장·기상 데이터를 통합해, 식품 커머스 MD·마케터가 누구에게, 언제, 어떤 신선식품을, 얼마에 팔지 결정하고 원가 위험 품목을 피하도록 돕는 수요·프로모션 의사결정 플랫폼이다.
